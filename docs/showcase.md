## `swarm-simulation` — живий рій агентів

- Брова: `The Big Picture` → **Загальна картина**.
- Заголовок: `Live Agent Swarm` → **Живий рій агентів**.
- Kicker: **П'ять агентів ШІ координуються в реальному часі: частинки-повідомлення, кольорові території файлів, завершення задач і миттєве виявлення конфліктів без людини в циклі.**
- Пояснення:
  - Модель показує сталий стан реального розгортання Agent Mail.
  - П'ять агентів зі сталою ідентичністю паралельно працюють в одній кодовій базі: надсилають повідомлення, резервують файли, завершують задачі, інколи конфліктують.
  - Конфлікти виявляються одразу, а не через години під час злиття.
  - Без центрального диригента: локальні рішення через ті самі інструменти MCP дають глобальну узгодженість.

## `conflict-cascade` — проблема конфліктів

- Брова: `The Problem Agent Mail Solves` → **Проблема, яку розв'язує Agent Mail**.
- Заголовок: `The Conflict Problem` → **Проблема конфліктів**.
- Kicker: **Без узгодження агенти тихо перезаписують роботу одне одного; з Agent Mail резервування запобігає конфліктам до змін у коді.**
- Пояснення:
  - Без узгодження пізніші правки знищують попередні, витрачаються обчислення і години людського розбору злиттів.
  - З Agent Mail агент спочатку резервує шаблон шляху; перетини блокуються з явним повідомленням про власника.
  - Із масштабом різниця лише зростає: те, що випадково працює для двох агентів, не працює для десяти.

## `token-economy` — економіка токенів

- Брова: `Why External Storage Matters` → **Чому важливе зовнішнє сховище**.
- Заголовок: `Token Economy` → **Економіка токенів**.
- Kicker: **Координація через чат спалює токени контексту; Agent Mail виносить координацію поза бюджет токенів.**
- Пояснення:
  - Кожен токен, витрачений на координаційний шум, не витрачається на розв'язання задачі.
  - Agent Mail зберігає повідомлення, гілки й індекси пошуку в зовнішньому архіві (Git + SQLite FTS5).
  - Виклики на кшталт `send_message` і `fetch_inbox` мають малу токенну вартість порівняно з безперервним чат-станом.

## `commit-coalescer` — об'єднувач комітів Git

- Брова: `Rust Engineering` → **Інженерія Rust**.
- Заголовок: `Git Commit Coalescer` → **Об'єднувач комітів Git**.
- Kicker: **Python-версія ламалась під навантаженням через блокування Git; перепис на Rust об'єднує часті записи у значно меншу кількість комітів (близько 9.1x стиснення).**
- Пояснення:
  - За одночасної активності багатьох агентів виникає суперництво за `index.lock`.
  - `write-behind queue` накопичує записи і зливає їх пакетним комітом.
  - Результат: різке зменшення кількості комітів без втрат даних і без тайм-аутів.

## `territory-map` — карта територій резервування

- Брова: `Spatial Awareness` → **Просторова видимість**.
- Заголовок: `Reservation Territory Map` → **Карта територій резервування**.
- Kicker: **Власність на файли видно як карту: агенти резервують шаблони шляхів, території підсвічуються, конфлікти блимають червоним, `TTL` запобігає глухим блокуванням після аварій.**
- Пояснення:
  - Резервування дорадчі, а не жорсткі.
  - Підсвічення показує, який агент утримує ділянку дерева файлів.
  - `pre-commit guard` дає другий шар захисту: випадкові порушення меж виявляються до потрапляння в репозиторій.

## `commit-coalescer-race` — змагання Python проти Rust

- Брова: `Python vs Rust` → **Python проти Rust**.
- Заголовок: `Commit Coalescer Race` → **Змагання об'єднувача комітів**.
- Kicker: **Розділений екран показує, як черга `write-behind` у Rust прибирає суперництво за блокування Git, властиве Python-реалізації.**
- Пояснення:
  - Python-коміт на кожне повідомлення веде до лавини `index.lock`.
  - Rust-черга об'єднує записи в пакети; у стрес-тесті 100 записів дають 11 комітів.
  - Відмінність видно в динаміці: ліворуч накопичуються збої, праворуч навантаження проходить чисто.

## `dual-write-pipeline` — двоконтурне зберігання

- Брова: `Architecture Deep Dive` → **Глибоке занурення в архітектуру**.
- Заголовок: `Dual Persistence Pipeline` → **Двоконтурний конвеєр зберігання**.
- Kicker: **Кожне повідомлення йде паралельно двома шляхами: SQLite для надшвидких запитів і Git для людяного перевірного архіву.**
- Пояснення:
  - SQLite дає швидкість і структурні запити.
  - Git дає читабельний, порівнюваний, довготривалий слід.
  - Розділення затримки запису та довговічності досягається через `write-behind queue` і `commit coalescer`.

## `backpressure-health` — трирівневий стан і протитиск

- Брова: `Reliability Engineering` → **Інженерія надійності**.
- Заголовок: `Three-Level Health & Backpressure` → **Трирівневий стан і протитиск**.
- Kicker: **Система постійно відстежує завантаження пулу, глибину WBQ і тиск черги комітів; у перевантаженні відсікає низькопріоритетні задачі, але критичні повідомлення проходять завжди.**
- Пояснення:
  - Сигнали: утилізація пулу, P95 очікування, глибина черги запису, черга комітів.
  - Стани: зелений → жовтий → червоний.
  - У червоному стані технічне обслуговування відсікається, а `fetch_inbox` і `send_message` зберігають прохідність.

- Пояснення:
  - Перевіряються реальні провали попередньої реалізації: блокування Git, виснаження пулу SQLite, каскадні збої.
  - Випробування підтверджують стійкість реєстрації, насичення WBQ, стабільність тривалого навантаження.
  - Набір запускається на кожному коміті, тож регресії ловляться до постачання.

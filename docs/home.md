## `home-concepts` — чому потрібна спеціалізована координація

### Заголовок секції

- `Why Purpose-Built Coordination` → **Навіщо спеціалізовано побудоване узгодження**.

### Пояснення

- Кожне проєктне рішення перевірене в бойовому режимі на 40–50 паралельних агентах різних постачальників у спільній кодовій базі.

### Концепт 1 — дорадче резервування файлів

- Агенти тимчасово резервують шаблони шляхів файлів.
- Резервування дорадчі й мають строк дії (`TTL`), тому немає глухих блокувань.
- Якщо агент аварійно завершується або втрачає стан, прострочене резервування очищується автоматично.
- За потреби можна додати примус через `pre-commit guard`.

### Концепт 2 — чому не `git worktrees`

- `git worktrees` знижують темп розробки та накопичують борг злиття.
- Єдиний спільний робочий простір із резервуванням показує конфлікти відразу.
- Гілкові повідомлення дозволяють узгоджувати межі задач у реальному часі.

Порівняння:

- **Git Worktrees:** борг злиття росте непомітно, розходження виявляється пізно, багато копій репозиторію, втрата роботи при невдалих злиттях.
- **Agent Mail:** конфлікти видно одразу, резервування запобігає зіткненням, один спільний простір, нульовий борг злиття.

### Концепт 3 — напівстала ідентичність

- Кожен агент має запам'ятовуване ім'я (`GreenCastle`, `BlueLake`, `RedHarbor`).
- Ідентичність живе протягом задачі й може зникнути без руйнування стану узгодження.
- `TTL` очищає сліди відсутніх агентів, `contact handshake` відновлює довіру при повторному вході.

### Концепт 4 — адресність замість загального мовлення

- Наївний підхід надсилає все всім і засмічує контекст.
- Agent Mail надсилає повідомлення адресно: тема, гілка, явні одержувачі.
- Відстеження підтвердження отримання гарантує опрацювання критичних повідомлень.

### Концепт 5 — пріоритезація задач за графом залежностей

- За великої кількості задач неефективно обирати випадково.
- `bv` використовує сигнали теорії графів, щоб радити найкращу наступну задачу.

Сигнали графового аналізу:

- `PageRank` — структурна важливість.
- `Betweenness` — виявлення вузьких місць.
- `Critical Path` — найдовший ланцюг залежностей.
- `What-If` — прогноз каскадного впливу.

### Концепт 6 — перевірка масштабом

- Система працює з 40–50 одночасними агентами (`Claude Code`, `Codex CLI`, `Gemini CLI`) у межах одного проєкту.
- Стресовий набір із 10 сценаріїв перевіряє конвеєри повідомлень на 30 агентів, відновлення після виснаження пулу, обробку "гуртових ударів", очищення застарілих блокувань і змішані навантаження `~49 RPS`.
- Усі сценарії проходять без помилок.

5. **Гібридний пошук V3** — двошарове злиття лексичного й семантичного пошуку з повторним ранжуванням.

10. **Запобіжник перед комітом** — блокує коміт у файли, зарезервовані іншими агентами.
11. **Керування слотами збірки** — контроль паралельних важких збірок.
12. **Чотири макроси сеансів** — типові багатокрокові дії одним викликом.
13. **20+ ресурсів MCP** — швидкий доступ до вхідних, гілок, агентів, резервувань, метрик і стану.
14. **Веб-інтерфейс операторського нагляду** — єдина вхідна для всіх проєктів, пошук і форма Overseer.
15. **Масштабна стресова перевірка** — 30 агентів, 10 проєктів, відновлення після критичних режимів.

## `workflow-deltas` — що реально змінюється

### Заголовок секції

- `Before & After` → **До і після**.
- `What Changes` → **Що змінюється**.
- Пояснення: **Реальні щоденні сценарії багатoагентної роботи і те, як спеціалізований координаційний шар змінює результат.**

### Сценарії

1. **Два агенти редагують той самий файл**
   - Без Agent Mail: тихе перетирання, втрачені години, конфлікт видно надто пізно.
   - З Agent Mail: резервування виявляє конфлікт до старту роботи; агенти узгоджують межі через гілкові повідомлення.
   - Ефект: **Нуль втрачених правок через файлові зіткнення.**
2. **Ізоляція через `git worktrees`**
   - Без Agent Mail: накопичується прихований борг злиття, розходження видно запізно.
   - З Agent Mail: агенти працюють у спільному просторі, а конфлікти спливають відразу.
   - Ефект: **Прибирається борг злиття як клас проблем.**
3. **Агент падає або втрачає контекст посеред задачі**
   - Без Agent Mail: залишаються застарілі блокування і немає ясної картини, що саме агент робив.
   - З Agent Mail: `TTL` очищає резервування, а архів Git зберігає слід дій.
   - Ефект: **Система самовідновлюється без ручного прибирання.**
4. **Агенти розсилають оновлення всім підряд**
   - Без Agent Mail: контекстні вікна забиваються шумом, витрати токенів ростуть.
   - З Agent Mail: повідомлення адресні, гілки явні, підтвердження не дають загубити критичні сигнали.
   - Ефект: **До 10x менші витрати токенів на координацію.**
5. **Масштабування з 3 агентів до 30+**
   - Без Agent Mail: не видно, хто що робить, конфлікти множаться.
   - З Agent Mail: реєстр агентів, резервування і пріоритезація задач дають керований ріст.
   - Ефект: **Координація зберігається навіть під великим паралелізмом.**

### Практична користь

- Ця секція відповідає на головне запитання скептика: **що конкретно стане кращим у моєму процесі вже завтра, а не в абстрактному "майбутньому рою агентів".**

## `reliability` — перевірені цифри

### Заголовок секції

- `Proven Reliability` → **Підтверджена надійність**.
- `Battle-Tested Numbers` → **Цифри, перевірені навантаженням**.
- Пояснення: **Кожне твердження про надійність підкріплене відтворюваними вимірюваннями або стресовими сценаріями.**

### Ключові твердження

1. **Production-ready at scale** → **Готовність до виробничого масштабу**
   - Доказ: 10-сценарійний стресовий набір покриває конвеєри повідомлень, виснаження пулу, "гуртовий удар", очищення застарілих блокувань і змішані навантаження.
   - Метрика: **10/10 сценаріїв проходять без помилок.**
2. **Low-latency coordination** → **Низькозатратна координація**
   - Доказ: у змішаному профілі навантаження оброблено `1494` операції за 30 секунд.
   - Метрика: **~49 RPS сталої пропускної здатності.**
3. **Minimal Git overhead** → **Мінімальний тиск на Git**
   - Доказ: об'єднувач комітів зменшує write amplification під час архівування.
   - Метрика: **приблизно 9.1x зменшення записів (`100` записів → `11` комітів).**
4. **Works with any MCP-capable agent** → **Працює з будь-яким агентом, що підтримує MCP**
   - Доказ: одночасні змішані сеанси з Claude Code, Codex CLI і Gemini CLI.
   - Метрика: **40-50 одночасних агентів від різних постачальників.**
5. **Robust to agent failures** → **Стійкість до падінь агентів**
   - Доказ: спливання `TTL`, виявлення застарілих блокувань, автоматичне очищення.
   - Метрика: **нуль ручних втручань для відновлення після падіння агента.**

### Практична користь

- Цей блок важливий не для "краси цифр", а щоб відрізнити Agent Mail від демо-систем, які працюють лише на двох агентах і ламаються під справжнім навантаженням.

## `objections` — типові заперечення

### Заголовок секції

- `Common Objections` → **Типові заперечення**.
- `Honest Answers` → **Чесні відповіді**.
- Пояснення: **Причини, з яких команди зазвичай відкладають координаційний шар, і чому ці причини не витримують технічного розбору.**

### Заперечення і відповіді

1. **"Ми вже використовуємо Git-гілки для ізоляції"**
   - Відповідь: гілки ізолюють код, але не комунікацію; Agent Mail додає шар координації, якого Git не має.
   - Підстава: таблиця порівняння показує прогалини `git worktrees` у повідомленнях, ідентичності, пошуку й операторській видимості.
2. **"Це занадто ускладнює робочий процес"**
   - Відповідь: Agent Mail — це один двійковий файл, один запуск `am` і один стартовий макрос замість окремих брокерів, БД і хмарних сервісів.
   - Підстава: стартовий шлях займає менше хвилини.
3. **"Дорадчі блокування не масштабуються"**
   - Відповідь: масштабування тримається не на жорстких блокуваннях, а на видимості конфліктів, `TTL` і необов'язковому запобіжнику перед комітом.
   - Підстава: стресовий набір уже покриває 30 агентів і змішані навантаження.
4. **"Я не хочу залежати від ще одного інструменту"**
   - Відповідь: система локальна, відкрита і тримає дані в Git та SQLite.
   - Підстава: немає потреби в хмарній залежності для базової функціональності.
5. **"Наші агенти і так працюють без координації"**
   - Відповідь: так здається до першого реального конфлікту по файлу або втрати контексту між сесіями.
   - Підстава: саме ці збої Agent Mail і прибирає з базового робочого циклу.

### Практична користь

- Ця секція корисна, коли треба обґрунтувати впровадження системи команді або керівнику, а не лише "зрозуміти продукт для себе".

## `creator-insights` — погляд автора

### Заголовок секції

- `From the Creator` → **Від автора**.
- `Design Philosophy` → **Філософія проєктування**.

### Ключові тези

1. **Worktrees suck and just kick the can down the road** → **`git worktrees` не прибирають проблему, а відкладають її**
   - Сенс: ізоляція без координації накопичує борг злиття замість розв'язання конфлікту в моменті.
2. **It sidesteps the footguns that naive implementations hit** → **Система обходить типові пастки наївних реалізацій**
   - Сенс: ідентичність, адресні повідомлення, `TTL` і перевірний слід не є "надлишком", а є запобіжниками від класичних збоїв.
3. **You want semi-persistent identity** → **Потрібна напівстала ідентичність**
   - Сенс: агент може зникнути, але модель координації не повинна ламатися разом із процесом.
4. **Graph analysis is a compass** → **Граф залежностей працює як компас**
   - Сенс: пріоритезація задач у рої агентів має спиратися на структуру залежностей, а не на випадковий вибір.
5. **First open-source cross-provider coordination system** → **Перша відкрита координаційна система між постачальниками**
   - Сенс: Agent Mail задумано як інфраструктуру, що не прив'язує вас до одного клієнта чи одного постачальника.

### Практична користь

- Цей блок дає не маркетинговий слоган, а короткі проєктні принципи, через які легше зрозуміти, чому система виглядає саме так, а не інакше.

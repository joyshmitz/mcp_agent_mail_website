- Заголовок: `Get Started` → **Початок роботи**.
- Підпис: **Встановіть MCP Agent Mail, запустіть сервер і виконайте перший багатoагентний робочий цикл із резервуванням файлів.**

## `install` — крок 1: встановлення

- Брова: `Step 1` → **Крок 1**.
- Заголовок: `Install` → **Встановлення**.
- Kicker: **Встановіть двійковий файл рекомендованою однорядковою командою.**

  - `Copied` → **Скопійовано**.


## `example` — крок 2: перший робочий цикл

- Брова: `Step 2` → **Крок 2**.
- Заголовок: `Run Your First Coordination Flow` → **Запустіть перший цикл узгодження**.
- Kicker: **Запустіть `am`, зареєструйте агента, зарезервуйте файли і координуйтеся через гілкові повідомлення.**

Приклад (переклад коментарів і текстових полів):

```txt
# 1) Запустити сервер MCP Agent Mail + TUI
am

# 2) Ініціалізувати контекст сеансу одним викликом
macro_start_session(
  project_key="/abs/path/to/repo",
  program="codex-cli",
  model="gpt-5"
)

# 3) Зарезервувати файли перед редагуванням
file_reservation_paths(
  project_key,
  agent_name,
  ["src/**"],
  ttl_seconds=3600,
  exclusive=true
)

# 4) Узгоджувати роботу через гілкові повідомлення
send_message(
  project_key,
  sender_name="GreenCastle",
  to=["BlueLake"],
  subject="Починаю переробку автентифікації",
  thread_id="FEAT-123",
  ack_required=true,
  body_md="Маю резервування на src/auth/**; беру логін і ротацію токенів."
)
fetch_inbox(project_key, agent_name)
acknowledge_message(project_key, agent_name, message_id)
```

## `pillars` — базові принципи

- Брова: `Core Patterns` → **Базові шаблони**.
- Заголовок: `Three Pillars` → **Три опори**.
- Kicker: **Підвалини безпечного багатoагентного виконання в масштабі.**

### 1) Scoped Agent Identity

- Переклад: **Ідентичність агента в межах проєкту**.
- Зміст: ідентичності у межах проєкту, безперервність гілок і чітка семантика вхідної скриньки утримують паралельних агентів в узгодженому стані.

### 2) Reservation Guardrails

- Переклад: **Запобіжники резервування**.
- Зміст: дорадче резервування файлів і необов'язковий захист перед комітом роблять власність видимою до редагування і безпечнішою під час коміту.

### 3) Auditable Workflows

- Переклад: **Перевірні робочі процеси**.
- Зміст: повідомлення, підтвердження і сліди пошуку запитуються у SQLite та зберігаються в перевірному архіві Git.

## `use-cases` — типові робочі сценарії

- Брова: `Real-World Workflows` → **Робочі сценарії з практики**.
- Заголовок: `Use Cases` → **Сценарії використання**.
- Kicker: **Конкретні випадки, де координація через Agent Mail відділяє керований паралелізм від хаосу.**

### 1) Rapid Multi-Agent Prototyping

- Переклад: **Швидке багатoагентне прототипування**.
- Суть: запуск 10+ агентів на новому проєкті, вибір найкорисніших задач через графовий аналіз, уникнення конфліктів через резервування файлів, узгодження меж API через гілкові повідомлення.
- Результат: **Робочий прототип за години, а не за дні.**

### 2) Large-Scale Codebase Refactoring

- Переклад: **Велике рефакторинг-перепланування кодової бази**.
- Суть: план робіт розкладається на задачі з залежностями; агенти забирають окремі частини, резервують уражені файли й координуються через `thread_id`, пов'язаний з ідентифікатором задачі.
- Результат: **Рефакторинг десятків файлів без конфліктів злиття.**

### 3) Cross-Repository API Migration

- Переклад: **Міжрепозиторна міграція API**.
- Суть: фронтенд і бекенд пов'язуються через шину продукту; агенти на бекенді повідомляють агентів фронтенду про зміни контракту через міжпроєктні повідомлення.
- Результат: **Узгоджена міграція через межі репозиторіїв.**

### 4) 24/7 Continuous Development

- Переклад: **Безперервна розробка 24/7**.
- Суть: агенти працюють змінами; новий агент заходить у thread через `macro_prepare_thread`, бачить попередню історію і продовжує роботу без втрати координаційного стану.
- Результат: **Безперервний поступ без втрати контексту між сесіями.**

### 5) Auditable Agent Operations

- Переклад: **Перевірні дії агентів**.
- Суть: кожне повідомлення, резервування і дія агента записується в SQLite і виводиться в архів Git.
- Результат: **Повний перевірний слід для кожного рішення агента.**

## Додатковий навчальний блок — матриця вибору макросів

| Макрос | Коли запускати | Що дає | Типова помилка |
|---|---|---|---|
| `macro_start_session` | На початку роботи в проєкті або після входу в нову сесію | Готує контекст проєкту, реєструє агента і підтягує вхідну | Використовувати як заміну thread-resume, коли насправді потрібно відновити конкретну гілку |
| `macro_prepare_thread` | Коли треба повернутися в уже наявну гілку або швидко наздогнати хід розмови | Дає зведення по thread і свіжий контекст по листуванню | Запускати без `thread_id`, сподіваючись, що макрос сам "вгадає" потрібний контекст |
| `macro_file_reservation_cycle` | Коли треба швидко взяти файли в роботу і потім охайно звільнити | Стискає цикл резервування в один контрольований виклик | Використовувати його без уточнення області шляхів, отримуючи надто широке резервування |
| `macro_contact_handshake` | Коли треба відкрити новий канал зв'язку з агентом або між проєктами | Запускає процедуру запиту і схвалення контакту | Намагатися писати напряму без попереднього рукостискання контакту |

## `faq` — поширені запитання швидкого старту

- Брова: `FAQ` → **FAQ**.
- Заголовок: `Common Questions` → **Поширені запитання**.
- Kicker: **Відповіді на типові питання налаштування й експлуатації MCP Agent Mail.**

### Q1

- Питання: **Чи треба налаштовувати кожного агента вручну?**
- Відповідь: **Ні. `am` автоматично виявляє поширені інструменти агентів кодування і може ініціалізувати підключення MCP. За потреби доступні й ручні фрагменти для Claude Code, Codex CLI та Gemini CLI.**

### Q2

- Питання: **Який найшвидший шлях почати роботу з репозиторієм?**
- Відповідь: **Запустіть `am`, далі використайте `macro_start_session` для реєстрації агента, отримання контексту вхідної скриньки і старту роботи з резервуванням одним кроком.**

### Q3

- Питання: **Резервування файлів — це обов'язкові жорсткі блокування?**
- Відповідь: **Ні. Це дорадчі координаційні примітиви з видимістю конфліктів і необов'язковим примусом перед комітом (якщо встановлено guard).**

### Q4

- Питання: **Як Agent Mail запобігає втраті історії повідомлень?**
- Відповідь: **Повідомлення записуються у SQLite для швидкого пошуку і експортуються до перевірного архіву Git для довговічної історії, придатної до ревізії.**

### Q5

- Питання: **Чи працює це через кілька репозиторіїв/проєктів?**
- Відповідь: **Так. Є пошук на рівні продукту, агрегування вхідних і міжпроєктні контактні сценарії для координації між репозиторіями.**

## Додатковий навчальний блок — відновлення після обриву сесії

Якщо агент зупинився посеред задачі, не треба намагатися "оживити" старий процес. Потрібно відновити координаційний стан.

1. Знову відкрийте той самий проєкт і переконайтеся, що `project_key` або `human_key` збігається з попередньою роботою.
2. Запустіть `am`, якщо потрібні TUI і локальний контекст оператора.
3. Викличте `macro_start_session(...)`, щоб знову прив'язати агента до проєкту і підтягнути вхідну скриньку.
4. Якщо робота велася в конкретній гілці, викличте `macro_prepare_thread(thread_id=...)`, щоб побачити стисле зведення й останні повідомлення саме по ній.
5. Перевірте, чи активні старі резервування:
   - якщо вони ще живі, подовжіть їх через `renew_file_reservations(...)`;
   - якщо вони вже спливли, запитайте їх знову через `file_reservation_paths(...)`.
6. Перегляньте `fetch_inbox(...)` і підтвердіть критичні повідомлення через `acknowledge_message(...)`, якщо вони вимагали підтвердження.
7. Лише після цього продовжуйте редагування; відновлення треба робити через стан системи, а не через здогадки про те, що "мало б лишитися в пам'яті" агента.
